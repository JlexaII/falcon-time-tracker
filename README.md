# TimeTrack — тестовое задание Falcon AI

Небольшое веб-приложение для учёта рабочего времени. **Используются только вымышленные сотрудники и задачи.**

## Возможности

- Добавление сотрудников.
- Запуск таймера с описанием задачи и остановка таймера.
- Запрет второго одновременного активного таймера для одного сотрудника (SQLite partial unique index).
- История записей и суммарное время по каждому сотруднику за выбранный период, включая пересечение интервала с границами периода.
- Данные хранятся в SQLite и остаются после перезапуска приложения.
- Пустой отчёт отображается корректно. Авторизация не требуется по условиям задания.

## Запуск

Требуется Python 3.10+.

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
# source .venv/bin/activate
pip install -r requirements.txt
python app.py
```

Откройте http://127.0.0.1:5000 . База `tracker.sqlite3` создаётся автоматически при первом запуске. При последующих запусках данные сохраняются.

## Тесты

```bash
python -m unittest discover -s tests -v
```

Проверяются: добавление сотрудника; запуск и остановка таймера; повторный запуск активного таймера (HTTP 409); повторная остановка; пустой отчёт; корректный интервал дат; сохранение данных при повторном создании приложения с той же базой.

## Технические решения

- **Backend**: Python / Flask, JSON API.
- **Хранение**: SQLite, параметризованные SQL-запросы и ограничения базы.
- **Frontend**: HTML, CSS, JavaScript без тяжёлого SPA-фреймворка.
- Время хранится в UTC, отчёты выбираются по календарным датам **UTC**. Время для активного таймера считается до момента формирования отчёта. Записи, пересекающие границу периода, учитываются только в части периода.
- Приложение ориентировано на локальное тестирование. Для публичного размещения потребуются сервер WSGI, настройки безопасности и постоянное хранилище.

### Проверки и исправления

- **SQLite / Windows WinError 32 (обнаружено при реальном запуске тестов на Windows)**: четыре теста завершались ошибкой при `TemporaryDirectory.cleanup()` из-за открытого файла `test.sqlite3`. Причина: стандартный `with sqlite3.connect(...) as db` автоматически завершает транзакцию, но **не закрывает** соединение. В `connect()` добавлен `@contextmanager`, в `finally` вызывается `db.close()`; при этом сохраняется commit/rollback через `with db`. После изменения тесты необходимо повторно выполнить на Windows и зафиксировать результат.
На этапе анализа кода особое внимание уделено потенциальным ошибкам:

- **Повторный старт таймера**: проверка только на frontend ненадёжна. Использовано ограничение `CREATE UNIQUE INDEX ... WHERE stopped_at IS NULL` на уровне SQLite и ответ 409.
- **Двойная остановка**: обновление `UPDATE ... WHERE stopped_at IS NULL`, повторный запрос возвращает 409.
- **Завышение отчётного времени**: суммируется только пересечение рабочей записи с заданными датами, а не вся длительность целиком.
- **Потеря данных**: SQLite-файл хранится на диске, а не в памяти, и повторная инициализация не очищает таблицы.
- **Безопасность отображения**: пользовательские строки вставляются в DOM через `textContent`, а не `innerHTML`.

Эти пункты описывают внесённые защитные решения и проверяемые сценарии; не следует представлять их как обнаруженные в продакшене дефекты.

## Демо-сценарий

1. Добавить вымышленного сотрудника «Иван Тестов».
2. Запустить таймер «Разработка API».
3. Попытаться запустить второй таймер для того же сотрудника — система выдаст ошибку.
4. Остановить таймер, открыть отчёт за сегодняшний день.
5. Перезапустить `python app.py`, убедиться, что сотрудник и запись сохранились.
6. Выбрать даты без записей — приложение покажет нулевые итоги.
